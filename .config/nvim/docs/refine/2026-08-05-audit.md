# Codebase Audit — Neovim config

**Date:** 2026-08-05
**Scope:** Full project audit of `/home/stephan/.config/nvim`: `init.lua`, `lua/**/*.lua`, `luasnippets/**/*.lua`. README and config metadata were read for conventions; lockfiles, generated/dependency files, binary/non-source assets were excluded.
**Source files analyzed:** 77

## Executive Summary

- **Total findings:** 16 (0 critical, 11 warning, 5 info)
- **Top 3 areas needing attention:**
  1. `lua/util/` has boundary drift: several modules are plugin integrations or project-specific actions despite README documenting util modules as dependency-light helpers.
  2. `lua/util/pack.lua` is the highest-risk maintenance hotspot: it owns plugin spec discovery, schema normalization, lazy loading, command UI, health-facing state, and public query APIs.
  3. Tooling/runtime paths contain small but real contract/performance traps: Mason skip mappings are unreachable, plugin `cond` predicates run twice, snippet reloads do global work on `DirChanged`, and Treesitter scans parser catalogs on every `FileType`.
- **Overall assessment:** The config is small and has a clear startup shape, with no circular local require graph and no orphan plugin/snippet files after accounting for Neovim conventions. The main maintainability cost is layer ambiguity: reusable helpers, plugin adapters, and project-specific workflows live in the same namespace.

## Dead Code

### Warning
- `lua/util/mason_ensure.lua:35` — `BIN_TO_MASON` tries to mark non-Mason binaries with `nil` values (`pint`, `rustfmt`, `goimports`, `php_cs_fixer`, `pint or php-cs-fixer`), but Lua drops nil-valued keys. The lookup at `lua/util/mason_ensure.lua:67-71` cannot distinguish "known non-Mason binary" from "unknown binary", so active install metadata in `lua/plugins/conform.lua:11-13` still passes `pint`, `goimports`, and `rustfmt` through to Mason. This makes comments and behavior disagree. Fix: add an explicit `SKIP_MASON = { pint = true, rustfmt = true, goimports = true, php_cs_fixer = true }` checked before `BIN_TO_MASON`.

### Info
- `lua/util/map.lua:54` — `M.v()` is unused in the scoped source set. Existing visual mappings use `map.batch(..., { mode = "v" })`, `map.x()`, or `map.map({ "n", "v" }, ...)`. Extra unused helper shapes make contributors choose between conventions without evidence. Fix: remove `M.v()` or standardize an existing visual-only mapping on it.

## Coupling

### Warning
- `lua/util/pack.lua:202` — `util.pack` is a god module: one file discovers plugin specs, normalizes the spec schema, calls `vim.pack.add`, registers build hooks, implements lazy event/filetype/command/key triggers, runs plugin setup/key callbacks, exposes query state, and owns `:Pack`. A loader behavior change can regress unrelated command, health, or keymap paths. Fix: keep `require("util.pack")` as the facade, but split internals into discovery/normalization, load/trigger registration, and command/status modules.
- `lua/util/mason_ensure.lua:43` — Mason auto-install logic directly requires `config.lsp.servers` and reads raw plugin spec internals via `pack.specs()`; `lua/plugins/mason.lua:23` also reaches into `config.lsp.servers` for automatic-enable names. Changing LSP declarations or plugin `install.binaries` metadata requires auditing multiple unrelated consumers. Fix: expose one explicit tooling contract, such as `config.lsp.names()`, `config.lsp.mason_packages()`, and `util.pack.install_binaries()`.
- `lua/util/pickers.lua:3` — `util.pickers` is a Snacks-specific facade, and the same plugin-bound pattern appears in `lua/util/markers.lua:69`, `lua/util/snippets.lua:229`, `lua/util/dap.lua:330`, and `lua/util/native_tools.lua:64`. This conflicts with the documented helper boundary and makes removing/replacing a plugin require searching generic utility modules. Fix: move plugin-bound helpers to a `lua/config/integrations/` or plugin-owned support layer, or update the architecture docs to make that layer explicit.

## Portability & Reusability

### Warning
- `lua/util/pickers.lua:4` — every exported picker calls `require("snacks")`, and `grep_finder` reaches into `snacks.picker.source.grep` at `lua/util/pickers.lua:52`. The module is useful, but it is not backend-agnostic utility code. Fix: relocate it to a Snacks integration module or inject picker functions if a reusable abstraction is desired.
- `lua/util/mason_ensure.lua:47` — the installer derives package names from this config's LSP table and plugin spec schema, then registers Mason commands. It cannot be reused without this exact Neovim config layout and Mason registry plugin. Fix: move it under the Mason integration or pass server/spec data as inputs.

### Info
- `lua/util/blade_nav.lua:16` — Blade navigation walks upward for `resources/views` and resolves Laravel/Blade tokens. This is project-framework behavior, not generic utility behavior. Fix: move it to `lua/config/actions/blade_nav.lua` or `lua/config/laravel/blade_nav.lua` and update `lua/plugins/blade-nav.lua` callsites.
- `lua/config/lsp/servers.lua:3` — the server registry mixes generic LSP declarations with local `mise` Node resolution from `~/.config/mise/config.toml`. Reusing the table on another machine requires understanding local toolchain policy. Fix: move executable resolution to a small config-local toolchain helper and let Intelephense call that helper.

## File Organization

### Warning
- `lua/util/dap.lua:55` — `util.dap` combines project-kind detection, project-local templates, scratch-buffer documentation, DAP adapter/UI setup, Mason DAP integration, base PHP/JS/Godot configurations, user commands, and extension registration in one 447-line module. Future DAP edits require reading unrelated template/help/setup paths. Fix: split setup, templates, help text, and extension API into separate DAP config modules; keep only a narrow facade if external `.nvim.lua` callers need `extend()`.
- `lua/util/snippets.lua:229` — `util.snippets` combines LuaSnip setup, VS Code snippet scaffolding, global/project snippet path management, editing/deletion commands, keymaps, reload logic, and embedded help. Contributors must understand loader behavior and UI/docs to adjust one command or path. Fix: split LuaSnip setup, file operations, command/keymap registration, and help text; keep pure file/path helpers separate only if they remain plugin-independent.

### Info
- `lua/util/blade_nav.lua:16` — Laravel/Blade-specific navigation is placed with generic utilities. Same root cause as the portability finding; fixing the location clarifies the module map.

## Interface Clarity

### Warning
- `lua/util/pack.lua:449` — `M.specs()` returns live mutable `state.specs` and `state.disabled` tables, including internal fields such as `_loader` and `_loaded`. `lua/health/pack.lua` and `lua/util/mason_ensure.lua` consume that raw shape. Callers can mutate loader state and are coupled to internals. Fix: return a copied/read-only view with documented fields and add targeted query helpers for health/install/status consumers.
- `lua/util/pack.lua:157` — the plugin spec guard is written as `type(spec) == "table" and spec.src or spec[1]`, so malformed modules that return no table can still index `spec[1]` before being ignored. The interface contract says plugin modules return specs; the guard should enforce that contract clearly. Fix: parenthesize and guard the shape: `elseif type(spec) == "table" and (spec.src or spec[1]) then`.

## Duplication

### Warning
- `lua/util/pack.lua:206` — `load_plugin()` evaluates `spec.cond` twice for function conditions: first via `pcall(spec.cond)` and then directly at `lua/util/pack.lua:209`. Future stateful or expensive conditions will behave unpredictably. Fix: call once with `local ok, enabled = pcall(spec.cond); if not ok or not enabled then return end`.

### Info
- `lua/util/dap.lua:56` — DAP configuration details are duplicated between `project_template()`, `M.open_help()`, and the actual base setup at `lua/util/dap.lua:389-438`. Ports, adapter types, names, `cwd`, `webRoot`, path mappings, and Godot settings can drift between user-facing help and runtime behavior. Fix: extract shared constants/builders or reduce help/templates to only show overrides that differ from the base config.

## Complexity

### Warning
- `lua/util/pack.lua:202` — the central pack loader has too many responsibilities in one control surface. Same root cause as the coupling finding; splitting discovery, loading, and command/status behavior reduces the cognitive load of changing plugin semantics.
- `lua/util/pack.lua:206` — the two-step `cond` handling is harder to reason about than a single guarded predicate call. Same root cause as the duplication/performance finding.

## Performance & Optimization

### Warning
- `lua/util/pack.lua:206` — successful plugin `cond` functions run twice. This doubles predicate work and makes side effects possible in a runtime loader path. Fix: one guarded `pcall` result.
- `lua/util/snippets.lua:267` — the `DirChanged` autocmd calls `load_user_collections()`, which reloads global Lua snippet paths at `lua/util/snippets.lua:82-86` before registering the new project-local directory. Directory changes redo global loader work even though the global path is static. Fix: split global and project loaders; call only project registration on `DirChanged`.
- `lua/plugins/treesitter.lua:69` — every `FileType` event scans `ts.get_installed()` and may scan `ts.get_available()` at `lua/plugins/treesitter.lua:74`. That allocates/scans parser catalogs per buffer. Fix: build installed/available set tables once and update the installed set after async installs complete.

### Info
- `lua/util/dashboard/tips.lua:10` — `M.random()` rereads both tip files and rebuilds the `lines` table on every call. Dashboard tip data is static during a session. Fix: cache the loaded tips in a module-local table and sample from it.
